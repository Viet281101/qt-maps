# Hanoi Vector Style Audit

Audit date: 2026-10-28

## Verdict

The current pale, road-dense map is primarily explained by the intentionally
minimal Unit 01b/03 tile schema and style. The rendered screenshot is consistent
with those inputs; this audit found no evidence that a renderer defect is needed
to explain the appearance. That is not the same as proving that every rendering
path is bug-free.

Claude's analysis is directionally correct, with these corrections:

| Claim | Verdict | Evidence or correction |
| --- | --- | --- |
| The production Hanoi style is generated by `write_style()` and packaged by `build_hanoi_package.py` | Correct | The package builder invokes `tools/generate_vector_fixture.py --real-style-only`, rewrites the local URL token, and stores the result as `style/style.json`. |
| The style has only three layers | Needs precise wording | The style has four render layers: one background plus three data-backed layers. The MBTiles schema has exactly three source layers: `building`, `transportation`, and `place`. |
| Roads are almost white, five pixels wide, and not classified | Correct | The only road render layer uses `#f8fafc` and a constant width of `5`, with no class or zoom filter. |
| Only one Hanoi label is rendered by the vector style | Correct | The symbol layer filters `class == city` and `name == Hà Nội`, then uses the hard-coded text `HÀ NỘI`. |
| No street labels exist anywhere in the app | Incorrect | The vector style has none, but `RoutingProbe.qml` adds route-derived street-name overlays at zoom 15 and above. These are not general basemap labels. |
| Layer names match OpenMapTiles | Partly correct | The names resemble common OpenMapTiles names, but this is a project-owned custom Planetiler schema, not the full OpenMapTiles profile. The full profile was intentionally rejected because it required additional unapproved inputs. |
| Local glyphs and sprites are not the current failure | Correct but incomplete | They are sufficient for the present Hanoi marker/label. The glyph generator contains only a tiny character set for `HÀ NỘI`; it cannot support general Vietnamese street or district labels. |
| A separate `transportation_name` source layer is required | Not established | The existing `transportation` layer already carries `class` and `name`. A line-placed symbol layer can label it unless later evidence justifies a separate source layer. |

## Current pipeline and contract

`tools/data-pipeline/unit01b-hanoi.yml` emits the following bounded z12-z15
source layers:

- `building`: all OSM building polygons;
- `transportation`: all OSM highway lines with `class` and `name` attributes;
- `place`: city/town points with `class`, `name`, and `name_vi` attributes.

`tools/generate_vector_fixture.py::write_style(real_data=True)` produces:

| Render layer | Source layer | Current presentation |
| --- | --- | --- |
| `background` | none | `#dbeafe` |
| `buildings` | `building` | `#94a3b8`, dark outline |
| `roads` | `transportation` | `#f8fafc`, constant width `5` |
| `labels` | `place` | only the Hanoi city marker and hard-coded label |

The generated package confirms `qtmaps-style-v1`, layer-schema version 1, and
the three source layers above. `MapPackageManifest` rejects a different style
contract or source-layer set, and the map-pipeline tests encode the same
contract.

## Why the map looks pale

- Dense Hanoi highway geometry is drawn with the same near-white five-pixel
  stroke regardless of road class or zoom. At city scale, those strokes occupy
  a large portion of the visible map.
- The background is light blue, not white. Without separate water, landuse, or
  park polygons, empty land and water cannot be distinguished semantically.
- Buildings have useful contrast, but there is no land hierarchy around them.
- The vector style provides no general street, district, neighborhood, park, or
  water labels. The few visible street labels are route-derived QML overlays.

Changing colors and widths will improve legibility immediately, but it cannot
create water, parks, or landuse polygons that are absent from the tile schema.

## Planning implications

1. Treat the source-controlled style as a product asset rather than generating
   it inside the synthetic-fixture script. Keep URL substitution deterministic
   and loopback-only.
2. Reuse `transportation.class` for road hierarchy and `transportation.name`
   for initial line labels; do not add a duplicate source layer without measured
   need.
3. Add the smallest useful contextual schema first: water and selected
   landuse/park classes. Expand place classes only with defined zoom and label
   rules. Defer POIs until their user value, icons, license, and density rules
   are specified.
4. Adopt a licensed Vietnamese-capable font/glyph pipeline before general
   basemap labels. The current handcrafted glyph fixture is diagnostic only.
5. Version the map-package layer schema and style contract together, rebuild an
   immutable package, update validator/tests, and compare Release performance
   against the locked Unit 06 baseline.

Implementation is specified in
`context/feature-specs/hanoi-cartography-style-upgrade.md`.
